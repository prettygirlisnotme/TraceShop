## 三分钟答辩稿

以下时段为讲解安排，可随现场语速调整。

**0:00–0:25｜问题与目标**

“TraceShop 把采购建议变成可确认、可核对的行动。用户给出需求、预算和硬关键词，Agent 研究候选、创建提案；宿主批准后，应用保存草稿并独立读回。演示用的是合成商品和三条官网快照，不会真实下单或付款。”

**0:25–1:05｜为什么购物**

“购物天然带检索、推荐/证据、可确认执行三条线。我们只做这条窄而完整的链路：预算和硬关键词是强约束，软偏好只认目录原始字段证据，候选和只读替代严格分开，保存必须由人批准。读回正确不等于模型解释永远正确——所以我们把事实、理由和授权分开处理。”

**1:05–1:45｜条件变化后的重办（用历史素材，须说明版本）**

“这里放的是历史 197305 的旧合成目录演示：先有一份人工建立的旧提案 12.99 美元，报价变到 14.94 后，旧确认被拒绝且没有写出草稿。用户把任务明确交给 Agent 重办，模型重新研究、重新创建提案，再经宿主批准后保存并独立读回。要点是：条件一变，研究、批准、核验全部重来。0.5.1 基线这套逻辑由 198242 人工 UI 检查覆盖，真实模型闭环由 198316 覆盖（198273 为历史失败）；0.5.3 新 main 暂无真实模型证据，其办理记录/完整回复由 198504 的固定协议零模型覆盖。”

**1:45–2:20｜动作边界与验证范围**

“模型调用保存不等于用户批准：宿主负责请求确认，业务核心在真正写入时再次检查需求、研究版本、报价版本和有效期。这是单用例验证，不代表 100% 自主；宿主还有 60 秒回调超时，最终回复靠显式历史同步取回，历史没有回合终态，仍需明确结束。首次授权后立即重试的根因还没定位。”

**2:20–3:00｜生态与后续**

“对 OctoSense 的可复用成果是这个完整应用示例：七个工具的契约、保存确认、执行时版本校验、选择依据落盘与历史恢复。源码与运行材料可供其他应用参考，目前尚无上游合并记录。后续先解决授权重试和回调问题，再接实时商品目录或在线检索服务。”

## 六个常见问答

1. **Agent 能操作到哪一步？**
   核心采购业务暴露七个工具。0.5.1 基线的真实 M3 的 198316 序列调用了其中五个（未单独调用 `catalog.select` / `proposal.read`）；这是一条已验证流程，不代表全部界面、平台和所有路径均已验证，也不适用于 0.5.3 新 main。

2. **为什么还要用户确认？**
   确认是用户对写入动作的批准。Agent 可以自主研究并发起保存请求，宿主批准后才执行；不会让模型替用户批准。保存后的独立读回证明业务字段是否一致。

3. **目录未证实意味着商品不支持该特征吗？**
   只表示本演示目录没有匹配字段，不作反面结论。有证据时返回原始 `field/value`，方便检查模型依据。

4. **报价变化时会怎样？**
   提案绑定创建时的需求和版本；写入时重新检查。历史 197305 中旧确认被拒绝且不产生草稿，由用户交给 Agent 重新研究、重新批准、重新核验。

5. **超时与首次授权重试解决了吗？**
   底层回调超时和首次授权立即重试尚未定位根因；历史同步能取回回复，但没有 turn 终态，仍须明确结束。RC5 人工 UI 由 198242 覆盖（13 项检查通过，零模型），真实模型由 198316 覆盖（`passed=true`，0.5.1 基线）；0.5.3 新 main 由 198504 固定协议零模型覆盖办理记录/完整回复，**不宣称 60 秒问题修复**。

6. **对 OctoSense 贡献是什么？**
   当前成果是可运行应用及工具契约、确认、版本校验、恢复与复现材料，可供同类应用复用；尚无上游合并记录。发布封存与 App Hub 审核按官方流程分别进行。

## 找工时怎样讲

重点解释三个取舍：为什么条件变化后要重新研究并重新批准，为什么读回正确不等于模型解释永远正确，为什么历史回复不代表任务已结束。可迁移的动线是“检索 → 证据 → 约束 → 批准 → 执行 → 读回”。当前检索是合成/快照目录上的规则决策；真实检索算法效果需要独立数据与评估。
