# TraceShop 演示与答辩提纲

适用当前独立 OctoScript 应用。下面是建议安排，不是主办方规定的格式。已公开素材来自 v0.4.0；0.4.1 只补中文、状态截图与发布配置。

## 一句话说明

TraceShop 把购物需求变成有证据的采购提案：Agent 提建议，用户明确确认，应用重新检查约束，保存后独立读回。

## 建议的 90–120 秒演示

| 段落 | 操作 | 观众应看到什么 |
| --- | --- | --- |
| 需求与证据 | 办公预设，预算 $30，研究商品 | 合成演示目录、最多三个候选、价格与事实依据 |
| 模型建议 | 选候选、请求审阅并采纳有效回复 | 模型理由与候选事实分开；采纳仍待确认，未保存草稿 |
| 报价变化 | 确认前模拟涨价，再确认旧提案 | 旧提案被阻止，不能用旧价格保存 |
| 确认与核验 | 重新研究、选择、明确确认，再查看草稿 | 新报价、草稿编号、独立读回一致；可演示重启恢复 |

真实模型等待时间取决于宿主和提供方。card-host 没有审阅服务时演示真实不可用提示，走人工路径；已有真实模型截图和记录可补充解释。不要把静态截图或旧录像说成现场回复。

## 三个值得讲清楚的设计

1. **建议和授权分开。** 模型建议需校验来源、版本、候选与截止时间，保存仍需用户确认。
2. **授权针对当前状态。** 输入、报价或版本变化使旧提案失效；确认前重查，避免保存旧商品或旧价格。
3. **结果需要验证。** 从存储读回并核对关键字段，才报告保存成功。

学习时在 [main.splash](../bundle/main.splash) 沿 research、pick、adopt_suggestion、confirm_draft、boot 追一次流程，不必先读历史 Web 原型。

## 答辩问题

| 问题 | 当前事实 |
| --- | --- |
| 是真实电商下单吗？ | 14 条商品为合成演示数据，保存本地采购草稿，无支付或物流 |
| Agent 真实调用了吗？ | v0.4.0 在固定未修改 standalone Rinx、packaged octos、CN MiniMax-M3 下完成过一条建议采纳、确认、读回 |
| 是 OctoSense Shell System Agent 吗？ | 当前证据是 standalone Rinx 本地 Agent peer；注入式 Shell System Agent 未验证 |
| 服务不可用怎么办？ | 如实显示失败，人工选择、确认和读回仍可用 |
| 下一步产品价值？ | 用户提供真实报价，记录出处、币种、时间和事实；同步数据流向，保留确认与读回 |
